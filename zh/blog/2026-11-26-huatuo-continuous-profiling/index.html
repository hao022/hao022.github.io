CPU、内存、I/O、IRQ：性能、延迟究竟来自哪行代码？

2026-11-26 HAO022 ProfilingPerformanceObservability

HUATUO（华佗）项目支持很多特性，其中之一就是今天分享的持续性能剖析，和其他项目不同，HUATUO 支持 CPU，内存，中断，IO，以及语言层面的全面剖析。

CPU 使用率升高、请求响应变慢、内存占用增长。监控能帮助我们找到异常节点或容器，但排查还要继续：这些开销来自哪里，对应哪段代码？ 下面结合八张火焰图，看看这些数据能提供什么线索，以及如何据此继续排查。

CPU 时间花在哪里，先从较宽的调用路径看起

这张 PostgreSQL on-CPU 火焰图中，既能看到查询执行、索引扫描，也能看到 tcp_sendmsg 及其后续的内核网络处理路径。有了这些调用栈，下一步排查就有了方向：如果查询执行占比较高，可以结合执行计划进一步检查；如果网络处理占比较高，则需要结合请求量、结果集大小和网络指标分析。火焰图中，栈帧的宽度表示所选统计维度的累计值，横向位置并不代表执行顺序。热点值得关注，但占比高也可能只是因为它承担了必要的工作。

CPU 使用率不高，线程却可能等了很久

图中较宽的路径经过：

PostgresMain → pq_getbyte → secure_read → epoll_wait

这说明，本次采集中有较多等待发生在这条读取路径上。此时需要结合请求到达情况和业务延迟，判断服务是在正常等待新请求，还是请求处理过程发生了阻塞。除了阻塞时间，off-CPU 还可以观察线程在运行队列中等待 CPU 的时间（例如，runqueue_preempted，runqueue_yielded，runqueue_missed_wakeup等细节）。图中的累计等待可能来自多个线程或进程，不能直接等同于单个请求的响应时间。

分析 Java 应用，还需要看到运行时内部的活动

这张图展示了 Elasticsearch、Lucene 的搜索路径，以及线程池和 JIT 编译相关的调用栈。有了这些信息，就能进一步区分 CPU 时间主要花在搜索执行、运行时编译，还是其他处理环节。

华佗项目支持系统层面以及语言（C、C++、Go、Java 和 Python）层面的剖析。

排查内存问题，先分清三种统计口径

virtual_alloc 记录虚拟地址空间的分配量。沿着图中的查询执行和元组处理路径，可以一直看到 mmap 相关调用，从而检查地址空间由哪些调用路径申请。

physical_alloc 记录采集窗口内的物理页分配量。通过图中的缺页处理路径，可以进一步检查哪些内存访问触发了物理页分配。

physical_usage 展示本次采样跟踪的物理页中仍然存活的字节数，以及这些页对应的分配路径。分配量较大或仍有物理页存活，都只能作为排查线索；单张图不足以证明内存泄漏。 内存模式与边界

Java 内存，要分别看对象分配与对象存活

object_alloc 展示采集期间的累计对象分配量，帮助查找分配热点和 GC 压力来源。图中主要涉及 Netty 缓冲区和 Lucene 搜索路径；累计分配量不等于当前堆占用。

object_usage 展示采样覆盖的存活对象及其分配路径。图中主要是 Netty 接收缓冲区的 byte[]，可进一步检查其复用与释放逻辑。两图不能直接相减；判断泄漏仍需结合增长趋势与引用关系。

自己跑一次，把火焰图与实际负载对应起来

在华佗仓库根目录启动开发栈：

make compose-dev-up

另开一个终端，启动 PostgreSQL 压测，分别进行 on-CPU 和 off-CPU 采集：

./build/docker/run_test_postgres_profiling.sh --oncpu --offcpu

要查看三种内存维度的结果，可以执行：

./build/docker/run_test_postgres_profiling.sh \
  --virtual-alloc --physical-alloc --physical-usage

要查看 Elasticsearch 的 Java on-CPU、对象分配与对象存活火焰图，可以执行：

./build/docker/run_test_elasticsearch_profiling.sh \
  --oncpu --object-alloc --object-usage

该脚本使用 Rally 产生搜索与聚合负载，分别采集 Java on-CPU、对象分配与对象存活数据。

脚本会部署临时服务、产生测试负载，通过 API 创建采集任务，并输出 Grafana 地址和结果目录。运行脚本需要本机具备 Kubernetes、containerd 及相关工具；开发栈中的固定凭据仅用于开发体验。

打开结果后，先确认采集目标、Task ID、时间范围和 Profile type，再分析调用栈。比较优化前后的结果时，应保持负载和采集条件一致。

持续性能剖析最有价值的地方，是将“服务为什么慢”这个宽泛的问题，拆解为几个可以验证的具体问题：哪条路径消耗了 CPU 时间，线程在哪里等待，哪些调用产生了内存分配。找到这些路径，再结合业务指标和系统事件逐步验证，才能明确应该优化什么，以及改动是否有效。
